# 解说视频匹配系统 — 从规则匹配到多模态检索的演进

> 作者：刘欢 | 时间：2026-05 | 用途：转正答辩

---

## 1. 背景与问题定义

### 1.1 业务场景

短剧解说视频自动生成：给定一部短剧（如《不好意思我喜欢你》、共 10 集），系统自动生成解说文案，为每句话匹配最合适的视频画面片段，最终合成完整解说视频。

### 1.2 核心挑战

```
输入: 解说文案（文本） + 短剧视频（N 集，每集约 20-30 分钟）
输出: 每句文案 → 匹配一个最合适的视频片段

难点:
  1. 搜索空间大：每集 100-200 个片段，10 集共 1000-2000 个候选
  2. 语义鸿沟：文案（"男主冷冷看了她一眼"）和视频之间的抽象层次差异
  3. 多维度匹配：角色、场景、动作、情绪、剪辑节奏需同时满足
  4. 标注困难：人工标注成本极高，且标准难以量化统一
```

### 1.3 系统目标

从"能跑通"→"跑得准"→"可评估可优化"，最终构造高质量 RL 微调数据集，训练专用 Cross-encoder Reranker。

## 2. 系统演进历程

```
V1 (smart_video)      V2          V3          V4            V5           V6
    │                   │           │           │             │            │
    ▼                   ▼           ▼           ▼             ▼            ▼
 原始匹配           +前20秒加权   +集数索引    +四阶段精排   +ASR时间映射  +多模态检索
 合并视频+切割      +多字段打分   +集内匹配    +动态权重     +直接切割     +Qwen3-VL-Embedding
 BGM/BERT embedding               +suoying    +LLM-as-Judge              +Cross-encoder Reranker
                                                 +plan.md路线图             +Canonical Judge评估
                                                                            +RL数据构造管道
```

### 2.1 V1 — 原始基线 (smart_video, 2026-01)

**输入**：将多集视频合并为一个长视频 → PySceneDetect 场景切割 → 多模态 LLM 理解每个片段 → 生成结构化描述文本

**匹配**：将文案文本 + 视频描述文本分别通过 BGM/BERT Embedding API（`10.163.166.76:17998`）向量化 → 余弦相似度 → Top-K

**管道**：S0(合并视频) → S1(视频结构化描述) → S2(embedding索引) → S3(文案拆分+TTS) → S4(余弦匹配) → S5(合成)

| 优点 | 问题 |
|------|------|
| 跑通端到端流程 | 合并视频导致集数信息丢失 |
| | 单路文本 embedding，丢失视觉细节 |
| | 匹配精度低，无精排 |

### 2.2 V2 — 前 20 秒加权 (smart_videoV2, 2026-02 初)

**核心变化**：引入"黄金前 20 秒"概念

- 前 20 秒文案：多字段加权匹配（script_text × actions × environment），权重 0.5:0.3:0.2
- 20 秒后：回退到简单单字段匹配
- 新增 `interaction_type`、`emotion_intensity`、`director_intent` 等 visual_query 字段

**效果**：前 20 秒关键内容匹配质量提升，但 20 秒后质量断崖式下降，整体不稳定。

### 2.3 V3 — 集数索引化 (smart_videoV3, 2026-02 中)

**重大架构重构**：不再合并视频，改为逐集处理

- 新增 `skill_video_episode_indexer.py`：每个视频片段标注所属集数
- 引入 `suoying` 模块：用 LLM 将每句文案映射到目标集数（episode_target）
- 匹配搜索空间从"全集"缩小到"单集"，噪声大幅降低

**管道**：S1(逐集视频索引化) → S2(按集分组 embedding) → S3(文案拆分+suoying) → S4(集内匹配) → S5(合成) → S6(final.json)

### 2.4 V4 — 四阶段级联精排 (smart_videoV4, 2026-02 中至 04)

**匹配引擎从单阶段升级为四阶段级联**：

```
Stage 1: 语义召回 → TOP 20  (文案 vs 视频 embedding 余弦相似度)
Stage 2: 视觉精排 → TOP 10  (角色/动作/环境/对话 加权，动态权重按文案类型调整)
Stage 3: 情感深排 → TOP 5   (互动/情绪/意图 加权)
Stage 4: LLM 终选 → TOP 1   (多模态 LLM 直接判断，当前已禁用)
```

**动态权重系统**：根据文案类型（emotion_action / balanced / action_heavy 等）自动切换 Stage2/Stage3 权重。

**其他新增**：
- `judge/` 目录：LLM-as-Judge 评估系统（5 维度打分：entity_match, event_match, scene_match, tone_match, editing_suitability）
- `doc/plan.md`：Phase 1-4 路线图（LLM-as-Judge → 多模态检索 → DPO Reranker → RL 优化）
- 文案生成增强：text0204.py + 去幻觉 + 格式校验

**局限性**：
- 仍然是文本→文本匹配，embedding 使用 BGM/BERT，视觉信息通过文本描述间接表达
- 四阶段权重硬编码，泛化能力有限
- Embedding API 吞吐受限，无法规模化

### 2.5 V5 — ASR 时间映射探索 (smart_videoV5, 2026-02 末)

**范式转变**：完全放弃语义匹配，改为 ASR 时间戳直接切割

```
文案 → suoyingnew（映射到集数+ASR时间戳） → 在ASR时间处直接切割原始视频 → 合成
```

- 新增 `skill_text_to_asr.py`：文案 → ASR 片段映射 + TTS
- 新增 `skill_asr_clip.py`：按 ASR 时间戳切割视频 + 合成

**结论**：ASR 对齐在某些场景有效，但精度依赖 ASR 质量，且无法处理"解说文案 ≠ 原始对白"的改写场景。作为补充路径保留，未替代主流程。

### 2.6 V6 — 多模态检索 + 评估闭环（当前版本, 2026-04 至今）

**核心升级**：用 Qwen3-VL 多模态模型替换传统 embedding + 规则精排，建立 LLM-as-Judge 评估闭环。

#### 架构对比

```
V4 (旧):  文案文本 → BGM/BERT embedding → 余弦检索 → 四阶段规则精排
                       ↑
          视频描述文本 → BGM/BERT embedding

V6 (新):  文案 (Q3 query) → Qwen3-VL-Embedding → 余弦 TopK → Cross-encoder Reranker
                       ↑
          视频多帧(纯视觉) → Qwen3-VL-Embedding
```

#### Query 版本体系

| 版本 | 文案侧信息量 | 构成 |
|:---:|---|------|
| Q1 | 最小 | 仅 script_text |
| Q2 | 少 | + 扩展标签 |
| Q3 | 中 | + 角色类型 + 动作 + 环境 + 互动关系 |
| Q4 | 最大 | + 模糊意图 JSON |

#### 视频侧版本体系

| 版本 | 视频侧表示 | 方法 |
|:---:|---|------|
| V1 | 纯视觉 | 多帧视频帧 → Qwen3-VL visual embedding |
| B1 | 视觉+文本 sidecar | V1 embedding + structured_description 文本 embedding 拼接 |
| B2 | 双路 Late Fusion | 视觉路 + 文本路独立检索，RRF 合并 |
| B3 | 双路加权 Fusion | B2 + α 权重可调 |

#### Canonical Judge 评估体系

**核心思想**：Judge 只跑一次，所有变体共享同一份评分矩阵

```
每条文案 × 目标集内所有视频片段 → Gemini-3-Pro 五维度全量打分
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
     变体A (V4)     变体B (Q3)    变体C (Q3+Reranker)
       查排名          查排名          查排名
```

**优势**：消除 LLM 每次重跑的随机波动，实现真正的公平对比。

**5 维度评分**：

| 维度 | 含义 | 权重 |
|------|------|:--:|
| entity_match | 画面人物是否与文案描述一致 | 25% |
| event_match | 画面动作/情节是否对应 | 25% |
| scene_match | 环境、氛围、时间是否符合 | 20% |
| tone_match | 情绪强度、叙事语气是否协调 | 15% |
| editing_suitability | 时长、构图、镜头连贯性 | 15% |

## 3. 解说文案生成系统演进

解说文案是匹配系统的上游输入，文案质量直接影响下游匹配效果。`video_commentary_text/` 模块经历了从简单生成到格式强校验+去幻觉+集数映射的逐步完善。

### 3.1 整体流程

```
输入: 剧名(dj) + 集数范围(start~end)
  │
  ├─ 1. 高级打标 (advanced_labeling.py)
  │     5 个主标签(爽快打脸/走心催泪等) + 次标签 + 强度打分(1-5)
  │
  ├─ 2. RAG 示例检索 (rag_retrieval_labeling.py)
  │     根据标签从 rag.jsonl 检索相似风格的参考文案
  │
  ├─ 3. 剧情事实提取
  │     PlotGraph: 人物/关系/原子事件(带证据)/节拍
  │     BeatSheet: 6段节奏规划(钩子→铺垫→冲突→反转→高潮→悬念)
  │
  ├─ 4. System Prompt 增强
  │     注入 RAG 示例 + 输出格式约束 + 对白禁止规则
  │
  ├─ 5. 文案生成 (text0204.py)
  │     Gemini-3-Pro, temp=0.45, top_p=0.85
  │     多轮迭代(最多3轮), 质量评估驱动
  │
  ├─ 6. 去幻觉检查
  │     对比 PlotGraph 检查矛盾/过度确定, 定点修补
  │
  └─ 7. 提取纯文本 (extract_final_script_to_text.py)
        提取"去幻觉后的解说文案" → 过滤30+噪声模式 → txt
```

### 3.2 各版本演进

| 版本 | 关键变化 | 新增文件 |
|------|------|------|
| V1 | 基础框架：打标+RAG+生成+去幻觉 | `text0204.py`, `fewshot7.py`, `advanced_labeling.py`, `rag_retrieval_labeling.py`, `skill_video_commentary_text.py`, `skill_video_commentary_quality_eval.py` |
| V2 | 无实质变化，workspace 重组 | - |
| V3 | 引入 `suoying.py`：文案→集数映射 | `suoying.py` |
| V4 | **格式强校验 + fail-fast** | `README.md` |
| V5 | `suoyingnew.py`：下沉到 ASR 时间戳对齐 | `suoyingnew.py` |
| V6 | 合并 suoyingnew 进 suoying，保留 V4 质量改进 | - |

### 3.3 V4 关键改进：从"能生成"到"生成对"

#### 输出格式硬约束

V1 时代模型经常输出 SOP 教程体、编号提纲等无效内容。V4 引入了两层校验：

**第一层 — 结构完整性检查** (`check_required_output_format`)：
```
必须按顺序包含: ## SOP 1 → ## SOP 2 → ## SOP 3 → ## SOP 4 → ## SOP 5 → ## 最终解说文案
缺失任一章节 → 判定格式失败，触发 retry
```

**第二层 — 正文可用性检测** (`detect_invalid_script_output`)：
```
12 个无效标记: "根据提供的信息，我们可以初步勾勒出"
              "由于缺乏详细的情节描述"
              "故事大致走向" 等
+ 编号提纲检测
+ 最小长度阈值: 120 字符
```

#### Fail-Fast 策略

```python
# V1: 提取失败 → 回退完整 raw_response（可能包含 SOP 噪声）
# V4: 提取失败 → 直接报错退出
#      避免 SOP/流程文本污染去幻觉和下游匹配
```

#### 5 次重试 + 定向修复

```
无评估模式:
  第1次: 正常生成
  格式失败 → retry prompt: "严格按固定结构重写"
  内容失败 → retry prompt: "避免'根据提供的信息'等套话"
  5次全失败 → RuntimeError (fail-fast)
```

#### 噪声过滤

`extract_final_script_to_text.py` 从 V1 的简单提取扩展到 30+ 噪声模式：
- Markdown 表格行
- SOP/方法说明标题
- 情节结构/节奏标注
- 冲突检查报告文本
- 7 类元信息行

### 3.4 suoying — 文案到集数映射

**核心问题**：解说文案是一段连续文本，需要映射到具体的视频集数，才能在该集内做匹配。

**V3 版本**（仅集数级映射）：
- 加载每集 ASR 前 20 句作为摘要
- LLM 逐句分派到集数（temp=0.1）
- 输出 `{sentence_idx, episode, confidence}`

**V5 版本**（下沉到 ASR 时间戳）：
- 新增 `suoyingnew.py`：`difflib.SequenceMatcher` 将每句对齐到具体 ASR utterance
- 窗口大小测试 1/2/3 个连续 utterance
- 输出增加 `asr_start_time, asr_end_time, similarity` 字段

**V6 版本**（合并优化）：
- 合并 `suoyingnew` 的功能到 `suoying.py`
- JSON 解析升级：括号平衡解析器替代简单正则
- 支持 tuple/dict 新旧格式向后兼容

## 4. V6 多模态检索系统技术细节

### 4.1 Embedding 模型配置

| 参数 | 值 | 说明 |
|------|:--:|------|
| 模型 | Qwen3-VL-Embedding-8B | 本地部署 |
| 视频采样率 | 3.0 fps | 建索引用，采样30帧 |
| 文本最长 | 32768 tokens | Qwen3-VL processor 上限 |
| 输出 | float16, L2归一化 | 节省存储，余弦=点积 |
| batch_size | 视频=1, 文本=8 | 视频受显存限制 |

### 4.2 Query 版本实现细节

```python
Q1: "男主走上前，冷冷看了她一眼"                           # 仅 script_text
Q2: "男主走上前...\n扩展标签: 情感对峙, 权力反转"            # + expanded_tags
Q3: "男主走上前...\n角色: 男主, 女主\n动作: 走近, 注视\n     # + 角色+动作+环境+标签+互动
     环境: 室内客厅\n扩展标签: 情感对峙\n互动关系: 冲突对抗"
Q4: Q3 + "\n模糊意图: {\"emotion_intensity\":\"高\",         # + fuzzy_tags JSON
     \"director_intent\":[\"营造紧张感\"]}"
```

### 4.3 Reranker 配置

| 参数 | 索引阶段(S4) | 重排阶段(S4.5) |
|------|:--:|:--:|
| 模型 | Qwen3-VL-Embedding-8B | Qwen3-VL-Reranker-8B |
| fps | 3.0 | 1.0 |
| max_frames | 30 | 8 |
| 精度 | float16 | bfloat16 |
| 方法 | 余弦相似度 | Cross-encoder 直接打分 |
| 速度 | 快 (批量embedding) | 慢 (逐对打分) |

### 4.4 Judge 评分细节

**5维度权重**: event(30%) > tone(25%) > entity(20%) > scene(15%) > editing(10%)

**Few-shot 示例**: 5 个精心构建的教学样本，覆盖从 1.0（完全错配）到 5.0（完美匹配）的全分数范围。

**一致性检查** (`evaluate_with_consistency`):
```
第1轮: 3次调用 → 若 std<=0.5 → 取中位数
        若 std>0.5 → 追加2次(共5次)
        若仍>0.5 → 标记 low_consistency
```

**视频传输**: 整个 mp4 通过 base64 编码为 `data:video/mp4;base64,...` 直接传给 Gemini。

### 4.5 RL 数据 Builder 分类规则

```
                    overall >= 4.5
                   /            \
              would_use?      would_use=false
              /      \              \
         conf>=0.8  conf<0.8    → unusable
           /            \
    strong_positive   → unusable

     2.5 <= overall <= 3.5
    /          \
 有高维(>=4)  来自系统topk  → hard_negative
    \
 有低维(<=2) & >=2高维  → dimension_negative

     overall <= 2.0  → easy_negative

     其余  → unusable (不进训练)
```

### 4.6 报告诊断标签

```python
def _diagnose_script(script_report):
    if n_candidates == 0:        → "无成功评估结果"
    if rank==1 and score>=4.0:   → "已命中高质量"
    if rank==1 and score<4.0:    → "命中但上限不足"
    if ge_4_count == 0:          → "候选池不足"
    if rank <= 3:                → "接近，可优化"
    else:                        → "有好候选但错排"
```

## 5. 实验过程与关键结论

### 5.1 实验规模

- **基准数据集**：6 部剧，28 个 query，849 条 Canonical Judge 评分
- **实验变体**：15 个（V4 + Qwen Q1/Q2/Q3 × V1/B1/B2 × 有/无 Reranker）
- **评估指标**：Hit@K、Recall@K、系统均分、>=4.0/>=4.5 达标率、平均分差

### 5.2 Step 1 — Recall@20 天花板分析

**问题**：embedding 复杂度提升真的有用吗？还是简单 embedding + 强 reranker 就够了？

| Variant | Oracle 均分 | >=4.0 候选数 | >=4.5 候选数 | 实际均分 |
|---------|:----------:|:----------:|:----------:|:------:|
| B1      | 4.391      | 102        | 70         | 4.03   |
| Q3      | 4.391      | 102        | 71         | 3.84   |
| Q1      | 4.388      | 94         | 66         | 3.77   |
| Q2      | 4.388      | 98         | 69         | 3.73   |
| V4      | 4.388      | 95         | 66         | 3.14   |
| B2      | 4.286      | 87         | 61         | 3.03   |

**关键发现**：
- **Oracle 均分极差仅 0.105** — 所有变体的 top-20 候选池质量几乎一致
- **实际均分极差 1.00**（3.03→4.03）— 差距完全来自排序能力
- **核心启示**：embedding 做得再复杂也没用，天花板已定，应该在 reranker（排序）上发力

### 5.3 Step 2 — 全因子实验

**Reranker 对弱 query 提升显著，对强 query 无效**：

| 变体 | 无 Reranker Hit@1 | +Reranker Q1 Hit@1 | 提升 |
|------|:---:|:---:|:---:|
| V1+Q1 | 28.6% | 35.7% | **+7.1pp** |
| B1+Q1 | 25.0% | 35.7% | **+10.7pp** |
| V1+Q2 | 32.1% | 39.3% | **+7.1pp** |
| V1+Q3 | 39.3% | 39.3% | 持平 |
| B1+Q3 | 39.3% | 39.3% | 持平 |

#### 综合排名 TOP 5

| 排名 | Variant | Hit@1 | 均分 | R@10 | >=4.5 | 判断 |
|:---:|---|:---:|:---:|:---:|:---:|---|
| 1 | `qwen_b1_q3` | 39.3% | 4.03 | 68.2% | 42.9% | 综合最佳，但依赖 B1 文本 sidecar |

```
      └─ groups.jsonl (GRPO/PPO 候选组: 每个 query 一组)
```

### 6.3 Bucket 分层策略

```
samples.jsonl → 按 overall 分数自动分层:
  ├─ strong_positive:    overall>=4.5 & would_use & conf>=0.8
  ├─ fallback_positive:  无强正时, overall>=4.0 & would_use
  ├─ hard_negative:      2.5<=overall<=3.5 & (有高维 or 来自系统topk)
  ├─ dimension_negative: 低维+高维共存
  ├─ easy_negative:      overall<=2.0
  └─ unusable:            其余（不进训练）

DPO 采样: strong vs hard (全量) + strong vs easy (采样2-3)
GRPO 采样: 每 query 保留全部正+hard+dimension + easy采样至15-20
```
